## 一、OpenHands 方案 A 回归（本阶段核心）

### 问题 1：SDK 1.21 新架构的三个"暗坑"

- **现象**：W3 曾因 openhands 拆分为全新 SDK（`openhands.sdk.*`，AppConfig/AgentController 消失）触发时间盒降级为方案 C。回归时逐个踩坑：①函数内写 `class` 语句建工具定义 → 事件落盘 `RecursionError`（"Local classes not supported"）；②工具参数键 `class`/`from` 是 Python 关键字 → 事件持久化回读报 `action.from Field required`；③`include_default_tools` 在 1.21 变成了 `list[str]` 语义（不再是布尔）。
- **解决方案**：①工具/Action/Observation/Executor 一律 `type()` 动态建类 + uuid 后缀注册键；②关键字参数用下划线字段 + alias，并显式 `populate_by_name=True`；③`include_default_tools=['FinishTool']`——只保留"任务完成"工具给模型明确收尾信号，同时排除 bash/文件等危险默认工具。
- **为什么这么解决**：这三个坑的共同点是"**库的版本演进使文档与假设失效**"。动态建类绕开判别式联合对 `<locals>` 类名的限制，是"适配库约束"而非对抗；保留 FinishTool 是为了让"最终答案"有确定信号可提取（final_answer 取自 finish.message），同时守住安全底线（评测环境不允许 agent 碰文件系统）。**回归任务最难的不是写代码，而是把新版本的真实约束一条条测出来**——这正是 W3 设时间盒、W4 单独排期的原因。

### 问题 2：真实接入的验证策略——单任务冒烟再全量

- **现象/决策**：方案 A 代码完成后，没有直接跑 O1/O2 两组 80 任务，而是先构造一个 tr_001 真实 run_spec，本地起 mock 服务跑一次适配器 CLI。
- **结果**：4.7 秒通过——真实 OpenHands 正确调用 `search_flights`（参数全对）、经 `finish` 工具收尾、答案只列上午航班、tokens 真实记入轨迹。
- **为什么**：这是第 2 次记录里"先小样本验证再全量"纪律的第三次实践（前两次：react 冒烟、MiMo 三探针）。计费 API 场景下，**每省一次全量重跑就是省一次真金白银 + 一轮时间**；冒烟产物（/tmp/trace.jsonl）同时成为可复查的验收证据。

### 问题 3：方案 C 数据 → 方案 A 数据的口径切换

- **现象**：O2 已有方案 C 数据（SR 0.85，2026-09-03 目录），方案 A 重跑产生新数据（2026-09-04 目录）——两套数据并存，报告不能混用。
- **解决方案**：①日期目录天然隔离（runs/2026-09-03_O2 vs 2026-09-04_O2），不做删除；②主表/分难度/失败分布/结论全面切换到方案 A 口径；③方案 C 数据保留为**历史对照**（如 sh_013 权限违规发现，方案 A 未复现，注明"历史发现"）；④dashboard 的三重过滤规则（排除 dryrun/failed/dry_run 目录）恰好自动只展示最新真实组。
- **为什么**：评测项目的**审计链**比结果本身更重要——删掉旧数据等于销毁"方案 C→A 演进"的证据；保留并标注，面试官才能看到你的决策轨迹。这也再次验证了第 1 次记录"实验产物按 run_id 归档、绝不覆盖"的架构决策在真实迭代中的价值。

## 二、实验发现类（方案 A 的最大回报）

### 问题 4：框架级发现——OpenHands 的提示体系会改变模型的"答案纪律"

- **现象**：tr_001（查询航班、答案必须只报上午）在真实 OpenHands 的 **O1（deepseek）和 O2（MiMo）双双失败**——而同一个 deepseek 模型在 react 框架下（R1）是通过的。模型工具调用全对，但最终答案"顺便"提及了本应过滤的下午航班。
- **定位**：对比两个框架的提示体系——react 适配器的 system prompt 是我们自己写的、明确要求"只输出 JSON 决策"；OpenHands 的 agent 循环有自己的提示模板与 finish 约定，模型在"更自由的叙事空间"里放松了过滤纪律。
- **为什么这是本项目最重要的发现之一**：**它直接证明了评测体系的存在价值**——如果不做框架横向对比，永远无法区分"模型不会过滤"和"框架提示削弱了过滤"。方案 C（react 循环贴 openhands 标签）时代根本发现不了这一点，因为 C 的提示体系就是 react 的。这正是"回归必须做"的最强论据：**真实框架差异只有真实框架能揭示**。

### 问题 5：真实 OpenHands 的画像——高效但多步易漏

- **现象**：O1 平均仅 8.8s/2.8 次工具调用（全实验第二快），但 L3 难度只有 0.8——失败集中在多段行程漏订第二段（tr_009）、退款链路缺验证/退款调用（tr_013）这类多步任务；deepseek 在 react/smolagents 下 L3 是满分 1.0。
- **解读**：OpenHands 的 agent 循环"快"是因为决策直接（少探索），"漏步"是因为缺乏 react 循环里"必须走完关键调用"的强约束。这给"选框架"提供了量化依据：**任务型场景要正确率优先（react/smolagents），效率敏感且步骤简单的场景 OpenHands 有优势**。

## 三、v1.2 落地补记（第 2 次记录发现问题 → 本阶段修复）

### 问题 6：两类评测器修正的落地与回归

- **空白归一化**：终态 equals 的字符串比较先去除全部空白（"88 号" vs "88号" 判等），数值/布尔不受影响；错误地址仍判负（归一化不放大水）。
- **端点抖动检测**：编排器连续 3 个任务 wall-clock 超时即中止本组并保留已记录行（断点续跑可恢复），避免 MiMo 挂死事故重演时烧穿整组预算。
- **为什么**：第 2 次记录的两条 v1.2 建议在此兑现——**评测器与评测基础设施必须随实验进化**，且每次修正都配回归测试（5 个新用例）保证"修尺子不折断尺子"。

## 四、面试叙述速记（STAR 更新版）

- **S**：多框架 Agent 评测体系，3 框架 × 2 模型 = 6 组真实对照实验。
- **T**：OpenHands 是最后一个未真实接入的框架（W3 时间盒降级方案 C），需要回归补上真实 SDK 驱动。
- **A**：SDK 侦察（签名/字段/事件流）→ 动态建类绕开三个新架构暗坑 → 单任务冒烟 4.7s 通过 → O1/O2 全量重跑 → 报告口径从方案 C 全面切换到方案 A（历史数据保留标注）。
- **R**：6 组矩阵全部真实（SR 0.90~0.975）；发现框架级新结论"OpenHands 提示体系削弱答案过滤纪律"（同一 deepseek 模型跨框架行为反转）；OpenHands 画像"高效但多步易漏"；全仓 273 测试全绿。

**一句话总结**（可背）：*"回归 OpenHands 最有价值的不是多了一列数据，而是发现同一模型在不同框架的提示体系下行为会反转——deepseek 在 react 里能严格过滤答案，放进 OpenHands 的 agent 循环就'答漏'了。这证明框架横向对比必须用真框架，任何'等价循环贴标签'的降级方案都测不出这种差异。评测体系的意义，就是在别人靠 anecdote 的地方，给出可复现的证据。"*
