## 一、评测器自省类问题（"发现我的尺子量错了"的续集）

### 问题 1：真实实验暴露 11 个 verifier 假阴性，且修正后历史结果不可比

- **现象**：R1/S1 共 14 个失败中 11 个是模型行为全对、verifier 判负——"21,680 元"查子串 "21680"（千分位）、"已**为您**取消"查"已取消"（措辞）；其中 2 例跨框架复现，证明与框架无关。
- **解决方案**：①数字检查改为 **Decimal 精确相等**（容忍千分位/小数，且防 "690" 误匹配 "6,900"）；②措辞关键词放宽（"取消"/"修改"）；③**实验期间冻结任务集**保公平；④写了**离线复评工具**（`analysis/reevaluate.py`）把历史结果按新尺子重判——R1 0.75→0.975、S1 0.90→0.95，不花一分 API 钱。
- **为什么这么解决**：改 verifier 后旧结果直接拿来对比会"污染实验"（新结果用新尺子、旧结果用旧尺子）。离线复评的难点是**终态没持久化**（运行时读的 mock 服务状态已销毁），所以复评只重判"答案维度"（findings 全为 answer_* 的行），绝不触碰调用/终态检查——**在数据缺失约束下做最小可辩护的修正**。这展示了做评测的核心素养：分清"模型失败"与"度量失败"，且修正要有审计路径。

### 问题 2：MiMo 实验又发现一类新假阴性——地址空白差异

- **现象**：S2 sh_003 模型把地址写成"…88号"，任务期望"…88 号"——工具接受（长度合法）、状态已改对，但终态检查是**字符串精确相等**，判负。
- **解决方案**：记入 v1.2 清单：final_state_checks 做空白归一化比较（实验后修）。
- **为什么**：与千分位同类——**度量工具的"格式敏感性"会持续产生假阴性**。每发现一类就固化一条校验清单项，让评测器随实验进化。

## 二、W3 模块开发中的问题

### 问题 3：OpenHands 接入按时间盒如实落地"方案 C"

- **现象**：安装 openhands 1.16/SDK 1.21 后发现是全新拆分架构（`openhands.sdk.*`，方案中假设的 AppConfig/AgentController 已不存在），自定义工具需按新事件架构重写；本机无 Docker（方案 B 前提缺失）；时间盒内无法稳定验证。
- **解决方案**：按 §6.5 预案触发**方案 C**：fake_llm 完整实现 + 真实模式为 react 等价循环，CLI 契约/预算/轨迹层不动，`_run_real` 是 W4 补 A 的唯一替换点；**如实记录"未接入真实 OpenHands"**。
- **为什么这么解决**：两条工程原则——①**时间盒决策要提前预案**（A→B→C 逐级降级，不临时拍脑袋）；②**不伪造能力**。评测项目里"假装接入了某框架"会在实验结果上制造系统性谎言；诚实降级 + 明确回补路径，比虚假的对比数据有价值得多。

### 问题 4：真实 judge 运行回退率 27/80

- **现象**：judge 用真实模型评分时 34% 的调用回退到 verifier 兜底分。
- **定位**：judge 的 `max_tokens=256` 太小——deepseek-v4-flash 是推理模型，**思考 token 计入 max_tokens**，256 被思考吃光 → content 为空 → JSON 解析失败 → 重试仍失败 → 兜底。
- **解决方案**：`JUDGE_MAX_TOKENS` 上调到 1024；重跑后回退率 27→5，agreement 0.93/0.97。
- **为什么**：这是"推理模型时代"的通用坑——**输出上限要给思考留预算**。同类问题第 1 次记录里出现过（适配器空 content），这次是同一个知识在不同模块的复用，说明"坑要沉淀成检查项"（judge 的 max_tokens 应随模型类型配置）。

## 三、重大基础设施事故：MiMo 端点挂死与连锁死锁（本阶段最有价值）

### 问题 5：单次模型调用挂死 82 分钟（端点"接受连接但永不返回"）

- **现象**：S2 最后任务 an_010 运行 82 分钟无进展，CPU 0%。
- **定位过程**（三层递进）：①`ps` 确认进程活着、CPU 0% → 网络等待而非计算；②macOS `sample` 抓调用栈 → 主线程阻塞在 **SSL socket read**——端点接受了连接但永不返回数据；③再查 litellm 的 `timeout=120` 参数为何没生效——**对该类挂死场景不生效**（超时只在特定链路层起作用，socket 阻塞读不被打断）。
- **解决方案**：**在适配器层用 daemon 线程 + join(120s) 做墙钟兜底**——超时抛 TimeoutError → status=timeout；worker 线程即使永久挂死也不影响进程退出（daemon 随进程回收）。三个适配器统一修复。
- **为什么这么解决**：外部依赖的保证不可信时，**把兜底放在自己可控的层**。线程 + join 是"不可杀线程"约束下唯一能强制返回的机制（Python 线程无法强杀），配合进程级超时强杀（编排器）形成双层保险。

### 问题 6：连锁反应一——smolagents 适配器 `interrupt()` 死锁

- **现象**：修端点挂死的过程中发现 smolagents 适配器有第二条死锁路径：worker 线程卡在模型调用（持锁）→ 主线程超时后调 `agent.interrupt()` 等同一把锁 → **主线程永远阻塞**，进程不退出，墙钟超时形同虚设。
- **解决方案**：超时分支**直接返回 EXIT_BUDGET，不再调 interrupt()**（worker 是 daemon，随进程退出回收）。
- **为什么**：`interrupt()` 的设计假设是"worker 能响应中断"，但**网络挂死时它不能**。超时路径必须是无锁、无条件返回的——这是"超时处理代码自身不能阻塞"的铁律。

### 问题 7：连锁反应二——编排器 `communicate(timeout)` 未按预期触发

- **现象**：适配器挂死后，编排器的 `proc.communicate(timeout=330s)` 理应强杀，实际 82 分钟都没触发。
- **解决方案**：弃用 communicate 超时机制，改**显式墙钟轮询**（`while proc.poll() is None and time.time() < deadline: sleep(0.5)`）+ `proc.kill()` + 收割——超时必然触发，不依赖任何库内机制。
- **为什么**：库函数的超时是"尽力而为"的语义（受管道、信号、平台实现影响）；**自己写的墙钟循环是确定性的**。监控/强杀类逻辑越简单越可靠。

### 问题 8：修复后的恢复策略——断点续跑 + 定点清理

- **解决方案**：①S2 只删掉被污染的 an_010 一行（CSV 行 + 轨迹 + spec），重跑编排器**自动只补跑这一个任务**（39 个已完成任务 SKIP，验证了断点续跑在真实事故中的价值）；②O2 因为混入了强杀产生的 error 行，整体重置全量重跑。
- **复验结果**：an_010 从挂死 82 分钟变为 98.9 秒通过；O2 全量 34/40 无一次挂死。
- **为什么**：评测系统必须**可恢复**——每次运行花真金白银，事故后的正确姿势不是"全量重来"，而是"定位污染范围、最小化重跑"。run_id 稳定 + 结果行幂等追加，让这个能力天然存在。

## 四、实验设计类问题（消融的方法论）

### 问题 9：第二 backbone 的选择与实验矩阵可插拔

- **现象/决策**：Qwen key 缺失，用户提供 MiMo-v2.5-Pro——直接接入而不是等 Qwen。
- **为什么**：消融组的本质要求是"**与主模型不同的、可用的模型**"，不是特定模型。评测管线全程模型无关（litellm 适配），换模型只改一处 YAML。这种"**实验矩阵与模型配置解耦**"的设计让实验不被单一供应商绑架。

### 问题 10：MiMo 三组全败于同一任务——模型级特征 vs 框架差异

- **发现**：tr_001（查询航班并要求只报上午）在 MiMo 的 R2/S2/O2 **三组全部失败**，deepseek 两组都过——模型会正确调用工具，但答案里"顺便"提及了本应过滤的下午航班。
- **价值**：这正是消融维度存在的意义——**如果只看单模型，会把"模型的过滤弱点"误判成"框架的弱点"**。控制变量矩阵让"模型效应"与"框架效应"可分离。同时 O2 出现全实验首个权限违规（误退他人订单），证明模型能力边界会改变失败模式分布，评测器必须对新的失败类型保持敏感。

## 五、面试叙述速记（STAR 更新版）

- **S**：多框架 Agent 评测体系，两模型 × 三框架共 6 组对照实验。
- **T**：第二 backbone（MiMo）消融 + judge 评分 + OpenHands 接入。
- **A**：接模型→三探针验证兼容→实验中发现端点挂死→`sample` 抓栈定位 SSL 阻塞→发现三层连锁缺陷（litellm 超时失效/interrupt 死锁/communicate 超时失效）→线程兜底+墙钟强杀三层修复→断点续跑定点恢复→离线复评保证新旧口径公平。
- **R**：6 组全景数据（SR 0.85~0.975）；框架效应跨模型成立、模型主效应分离；评测器两轮进化（v1.1/v1.2 清单）；一次 82 分钟挂死事故全程定位修复，复验通过。

**一句话总结**（可背）：*"做评测的第二课是：你的基础设施会以想不到的方式背叛你——端点挂死一次，能连环引爆框架库的超时失效、中断死锁和编排器的强杀失灵。我的解法是把兜底放在自己可控的最外层：线程墙钟 + 进程 SIGKILL + 断点续跑，让任何单点挂死都变成一条可审计的失败记录，而不是一个 82 分钟的悬案。"*
