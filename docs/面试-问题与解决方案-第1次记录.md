# AgentEval 项目实战记录 · 第 1 次记录

> 用途：面试时向面试官叙述"做这个项目时遇到了什么问题、怎么定位、怎么解决、为什么这么解决"的原始素材。
> 时间范围：W1（评测体系搭建）+ W2（smolagents 接入 + 首次真实模型实验）。
> 项目一句话：多框架 LLM Agent 工具调用评测体系——同一任务集、同一模型，横向对比自研 ReAct 与 smolagents 两个 Agent 框架，产出 SR/F1/成本/延迟与失败模式分析。

---

## 一、并行协作类问题（W1，3 个子代理并行开发时）

### 问题 1：三个模块并行开发，接口不一致会导致集成崩溃

- **现象/风险**：mock 工具服务、ReAct 适配器+编排器、指标模块由三个 AI 子代理并行实现，任何一方对"轨迹格式、CLI 参数、HTTP 契约"的理解偏差都会在集成时才爆发。
- **解决方案**：**契约先行**。主控先亲自落盘 `harness/protocol.py`（Trace/Step 数据类、run_spec.json 生成、trace.jsonl 读写、退出码 0/1/2），并做**文件所有权划分**（每个代理只许写自己名下的文件，互相只读）。三份任务书里把对方模块的函数签名、HTTP 端点、CSV 列序逐字写死。
- **为什么这么解决**：并行开发的最大风险不是代码量而是"接口漂移"。把唯一的共享依赖先冻结成可测试的契约（我还写了 protocol 的单元测试），集成时 7 个模块一次性导入成功、零接口返工——这是"接口先行"工程原则在多人/多代理协作里的落地。

### 问题 2：并行审查中抓出的 3 类真实缺陷

- **现象**：主控在集成前先跑各代理的测试，发现 (a) SQL 校验器放行 `SELECT 1; SELECT 2`（分号计数 `>1` 漏判单个非末尾分号）与非白名单表；(b) verifier 测试断言与引擎文档语义矛盾（字符串值一律子串匹配，测试却期望相等）；(c) 所有任务的原始模型日志写进同一个 `trace.raw.log`，多任务互相覆盖。
- **解决方案**：(a) 分号改为"只允许出现在语句末尾"，表名解析改为在保留空白的原文上做词边界匹配；(b) 修正测试断言并补充真实边界用例；(c) raw 日志改为 `{trace文件名}.raw.log` 每任务独立。
- **为什么这么解决**：评测系统的数据正确性是生命线——SQL 白名单被绕过会让"只读工具"变成可写漏洞；断言写错会掩盖真实回归；日志互相覆盖会丢失失败分析的关键证据。这类问题必须在实验开始前清零，因为**实验结果一旦产出，基于坏数据得出的结论无法事后补救**。

### 问题 3：lint 报错中"该修的"和"该豁免的"

- **现象**：集成前 ruff 报 16 个问题，混着两种性质完全不同的东西。
- **解决方案**：先分类——**刻意设计**（FastAPI 的 `Body()` 参数默认值 B008、评测装置对异常盲捕获 BLE001、run 目录用本地日期命名 DTZ011）在配置里声明豁免并写清理由；**真实缺陷**（未使用变量、嵌套 if 可合并、`subprocess.run` 缺显式 `check=False`）逐一修复。
- **为什么这么解决**：lint 是工具不是目标。评测装置鲁棒性优先（任何异常都要降级为兜底值而不是崩溃），所以盲捕获在这里是"特性"；但未使用变量这类问题没有辩护空间。面试官想看到的是**能区分"规则为什么存在"与"规则何时该让位"的判断力**。

## 二、真实环境 API 兼容性问题（W2 首次真实模型实验，最有技术含量）

### 问题 4：DeepSeek 推理模型拒绝带 tool_calls 的多轮消息（react 适配器）

- **现象**：单轮冒烟通过，但带工具调用的多轮对话报错 `The reasoning_content in the thinking mode must be passed back to the API`。
- **定位过程**：先用最小 litellm 脚本探测——发现 deepseek-v4-flash 是**推理模型**（响应分 `reasoning_content` 思考内容与 `content` 正文，且思考 token 计入 `max_tokens`）；再用三个探针区分：P1 纯文本续写（通过）、P2 合成 tool_calls 消息（被拒）、P3 assistant 原样输出 + user 消息回填工具结果（通过）。
- **解决方案**：把 react 适配器的工具结果回填从"标准 OpenAI 格式（assistant 带 tool_calls + role=tool）"改为"**assistant 消息原样回传 + 下一条 user 消息携带 `工具返回: {...}`**"。
- **为什么这么解决**：API 要求 tool_calls 消息携带模型真实生成的 `reasoning_content`，而适配器是"纯 JSON 协议"设计（不请求原生 function calling），合成消息根本拿不出合法的思考内容。与其伪造字段，不如换成 API 语义上完全合法的纯文本续写——最小改动、语义等价、且不依赖该端点未来是否继续支持 tool 角色。**"适配外部约束而非对抗外部约束"**。

### 问题 5：smolagents 适配器真实模式全线崩溃（0/40）

- **现象**：S1 组 40 个任务全部失败且每任务仅 1.1 秒（明显没发生真实模型调用）。读轨迹发现统一异常：`litellm.BadRequestError: LLM Provider NOT provided`。
- **定位过程**：对比 react（同样用 litellm，成功）与 smolagents（失败）的模型 ID 处理——smolagents 适配器为了"代码生成友好"把 `openai/deepseek-v4-flash` 的前缀剥成裸名 `deepseek-v4-flash`；而 litellm 对未收录的模型**必须靠前缀推断 provider**（openai 兼容端点走 `openai/` 路由），裸名直接抛错。
- **解决方案**：保留 litellm 的 provider 前缀原样传入；归档失败批次目录，修复后单任务冒烟通过，再全量重跑（36/40）。
- **为什么这么解决**：这次事故的教训是"**库的封装不是透明的**"——smolagents 的 LiteLLMModel 会把 model_id 原样转发给 litellm，任何"看起来无害的规范化"都可能打破底层路由约定。修复后用单任务冒烟（而非直接重跑 40 任务）验证，是为了不再花第二次冤枉钱——**先小样本验证再全量，是调用计费 API 的基本纪律**。

### 问题 6：模型调用没有客户端超时，单次挂起能拖死整个任务

- **现象**：监控中发现个别任务的首次 API 调用长时间无响应，而 litellm 默认客户端超时长达 600 秒，远大于任务预算的 300 秒。
- **解决方案**：react 适配器的 litellm 调用显式加 `timeout=120s`（可配置）；外层保留编排器的墙钟超时 + 进程强杀作为最终兜底。
- **为什么这么解决**：评测系统的预算语义要求"快速失败"——单次调用挂起 600 秒会让一个任务吃光整组的时间配额。120 秒的客户端超时 + 300 秒任务级超时形成两级漏斗，任何一层触发都会保留已产出轨迹并按失败计，保证实验总时长可控。

### 问题 7：推理模型的预算参数需要重校准

- **现象**：真实模型单任务耗时是 dry-run 的几百倍，L3 任务一次运行 50~100 秒；思考 token 计入输出消耗。
- **解决方案**：默认预算从 `timeout_s=180 / max_cost_usd=0.05` 上调为 `300 / 0.2`，并在配置里注明原因。
- **为什么这么解决**：预算不是"越低越好"——预算设太紧会把"模型本可以完成的任务"误判为失败（污染 SR 与失败分布）；设太松则失去保护意义。依据实测的 P95 耗时与 token 量重校准，是让指标可信的前提。

## 三、实验过程中发现的"元问题"（面试最有亮点的部分）

### 问题 8：14 个失败里 11 个是评测器自己的假阴性，而不是模型不行

- **现象**：R1 真实实验 SR=0.75，10 个失败；逐条读轨迹后发现：模型全部行为正确，失败是因为——答"**21,680** 元"而 verifier 查子串 "21680"（千分位）；答"已**为您**取消"而 verifier 查"已取消"；答"修改**为**"而 verifier 查"已修改"。其中 2 例在 smolagents 组**跨框架复现**，证明与框架无关。
- **解决方案**：实验期间**冻结任务集不改**（保证两组公平）；把发现写入报告，并列出 v1.1 修正清单（数字归一化匹配、措辞关键词放宽、工具描述补全、校验清单新增"自然表述变体鲁棒性"检查项）。
- **为什么这么解决**：这是评测项目独有的"元问题"——**你在度量模型，同时也在被自己的度量工具度量**。中途改 verifier 会让实验结果失去可审计性（面试官最忌讳"结果不好就改标准"）；而"发现评测器缺陷"本身就是高价值产出：它证明评测体系真的在运行、且作者有能力区分"模型失败"与"度量失败"。修正留到 v1.1 并全量重跑，则展示的是严谨的实验流程管理。

### 问题 9：两个框架的真实差异被数据揭示

- **现象**：smolagents 成功率更高（0.90 vs 0.75）但平均工具调用 3.5 倍、耗时 2 倍、token 4.7 倍；极端案例为一次退款任务**重试了 204 次工具调用**才成功；反过来 react 在一个"工具描述没写清返回字段"的任务上直接放弃而 smolagents 坚持尝试并成功。
- **解决方案/为什么值得讲**：不急着下"谁更好"的结论，而是把差异拆成三个正交维度——**成功率（效果）、调用数/耗时/token（效率）、失败模式（行为特征）**：smolagents 的 CodeAgent "执着但啰嗦"（恢复路径反复重试，甚至耗尽步数预算），react 的 JSON 协议"精简但易放弃"。这正是横向对比评测体系存在的意义：**没有这套装置，这些行为差异只能靠 anecdote，无法被量化**。

## 四、面试叙述建议（STAR 速记）

- **S（背景）**：要横向对比 Agent 框架，但现有评测（BFCL/τ-bench/SWE-bench）都做不到控制变量，所以自建了评测体系。
- **T（任务）**：我负责评测装置（harness）+ 任务集 + 两个框架适配器 + 真实模型实验。
- **A（行动）**：契约先行防集成冲突 → 最小冒烟防计费浪费 → 读轨迹定位 0/40 崩溃 → 探测 API 行为后改回填协议 → 预算重校准 → 冻结任务集保公平。
- **R（结果）**：80 次真实运行全量落地；发现 11 例评测器假阴性与 2 例真实失败；产出框架差异三维度结论；全部问题已定位、修复、复验并写入报告。

**一句话总结**（可直接背）：*"这个项目让我明白，做 Agent 评测最难的不是让模型跑起来，而是区分'模型失败了'和'我的尺子量错了'——14 个失败里 11 个是我的 verifier 对自然表述太苛刻，比如模型答'21,680 元'而我的检查在找子串'21680'。发现并修正这把尺子，比跑通实验本身更有价值。"*
